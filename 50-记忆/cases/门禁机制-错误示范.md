## 示范①：`sandbox = "none"` 未查合法枚举（2026-08-11）

**事实**
- 写 Codex 的 `config.toml` 时设 `sandbox = "none"`，未查 Codex 该字段的合法枚举
- 实际只接受 `elevated` / `unelevated`
- 结果：配置非法 → 回退 `elevated` → 每次启动强制安装 Windows 沙箱 → 弹窗死循环
- 且**被当成"已修复"上报**

**根因**
1. 未过门禁即动手（改配置文件属于门禁动作）
2. 完成判据用**推断**代替证据（"配置写了应该就好了"）
3. 命中「门禁总纲」第 3 条 —— **部分熟悉 ≠ 已确认**：见过 `sandbox` 字段 ≠ 知其合法枚举

**下次要坚持的**
- 凡涉及具体值 / schema，必须引用一手来源（`--help`、官方文档、源码）确认后再写
- 改配置后的判据是"启动无报错 + 行为符合预期"，不是"文件写进去了"

## 示范②：飞书写入凭印象选身份触发设备流（2026-08-12）

**事实**
- 手上有跑通的 `--as bot` 身份写法（案例2 / 案例4 + lark-unified 文档第 70 行明写 "Default identity: --as bot"）
- 却凭印象选了 `--as user`，触发浏览器设备流授权，白烧多轮

**根因**
1. 门禁触发描述"调用外部 API"太抽象 —— `lark-cli` 这类 CLI 调用在执行时未被识别为门禁动作
2. 「动作提案」缺"召回证据"字段 —— 门禁无法拦截"没读 cases 就动手"
3. 命中案例2 的反模式：**凭印象选路，不读自己已跑通的成功实现**

**架构层修复（已落地）**
- SOUL.md「第三方平台 API/CLI 调用 — 强制召回门禁」：触发改成**机械令牌命中**（命令含 `lark-cli` / `feishu` / `open-apis` / `--as user` / `--as bot` 即触发，不靠主观判断）
- 动作提案**必须**含 `recall_evidence` 字段（已读文件路径 + 关键结论），空则 critic ⛔拦截
- 增加「设备流断路器」：出现设备流 = 身份选错信号 → 立即停、回看历史成功身份、禁用同路径重发

**下次要坚持的**
- 有跑通的实现时，**先读自己的成功代码，再查文档**——已验证路径优先于文档路径
- `--as bot` 是默认身份：写用户空间无需浏览器授权；出现授权弹窗即身份选错了
