## 第2层·原因

**GBK 编码问题（本次最大浪费）：**
- 表面原因：Windows PowerShell 默认 GBK，Python print 含 Unicode 字符就炸
- 追问：为什么没想到？→ Windows + 中文环境每次都遇编码问题，但每次都是"遇了再修"
- 再追问：为什么没有形成预检习惯？→ 因为把它当"偶发问题"而非"确定性约束"

**`add_keywords` 未导入：**
- 表面原因：新增了调用代码，没更新 import
- 追问：为什么改了代码不跑一遍？→ 因为觉得"就加一行"不会有错
- 再追问：这个心态的根源？→ 对小改动过度自信，跳过了验证步骤

**中文引号语法错误：**
- 表面原因：f-string 中混用中文引号和 Python 字符串引号
- 追问：为什么用中文引号？→ 因为对话上下文中荣总用的是中文引号，直接复制了
- 再追问：这类错误可以预防吗？→ 可以，Python 代码中应该只用 ASCII 引号，这是确定性规则

**WiFi ADB 断连：**
- 表面原因：ADB daemon 自动重启
- 追问：能预防吗？→ 部分能，可以在脚本开头加 `adb connect` 重连逻辑

## 第3层·底层模型

> **「环境确定性约束的反复遗忘」**：Windows + 中文 + Python 是一个确定性会出问题的环境组合（GBK 编码、中文标点、Unicode 字符）。这不是"偶发问题"，而是"确定性约束"——每次在这个环境下工作都会遇到。但每次的处理方式都是"遇了再修"，而不是把它纳入预检清单。
>
> 这个模型与已有复盘的「行动优先 vs 确认优先」同源——知道会出问题但懒得提前防范，本质是对"确定性约束"的反应性而非预防性态度。

> **「小改动不验证」陷阱**：代码改动量与验证必要性不成正比——一行 import 遗漏和架构设计错误的后果相同（运行时炸）。但心理上会对小改动降低警惕。这是「行动优先」在微观层面的表现。

## 第4层·能力

**缺失「Windows 中文环境预检能力」：**
- 不是不知道 GBK 问题，而是没有把它固化为"每次写 Python 代码的第一步"
- 具体缺失：在 Windows 上写 Python 时，没有自动执行 UTF-8 强制声明 + ASCII 引号检查

**缺失「改动后即验证」能力：**
- 不是不知道要测试，而是对小改动有"不需要测试"的默认假设
- 具体缺失：没有"改完就跑"的强制习惯，尤其是 import/依赖类改动

## 第5层·基本功

**环境约束的反应性而非预防性态度：**
- GBK 编码问题已经出现过至少 3 次了（飞书 Wiki、抖音视频转文字、本次），但每次都是"遇了再说"
- 根本不是知识问题——知道 Windows GBK 会出问题；也不是能力问题——修复方式很简单
- 是**习惯问题**：把确定性约束当偶发事件对待，没有"这个一定会出问题所以提前处理"的肌肉记忆

> **基本功：在确定性约束面前，预防的成本永远低于修复。** 20min 的 GBK 修错，如果一开始就加 UTF-8 声明只需要 10s。

## 下次要坚持的
