# 案例10：飞书文档863篇垃圾写入（2026-05-05）

> 来源：`2026-05-05.md` 工作日志（一手记录）

**任务：** 把微信公众号文章批量写入飞书文档（承接案例9的 V2 方案）。

## 第1层·事实

1. 荣总发现863篇飞书文档全部是垃圾——内容只有本地文件路径（如 `C:\...\wechat-to-feishu\tmp\tmp_新韭菜八项注意.md`），没有文章正文
2. 根因：**lark-cli `--markdown` 参数接收的是 Markdown 内容字符串，不是文件路径**。原 `batch_feishu.py` 把**文件路径**当参数传入，lark-cli 把路径字符串当成了文档内容
3. 验证过程（5步）：
   - `docs +fetch --doc FHtzdadxGocI7SxWI71cBjTanyc` → 确认内容是文件路径
   - `docs +create --help` → 发现 `--markdown string  Markdown content (Lark-flavored) (supports @file, - for stdin)`
   - 测试 `@file` 语法 → 报错"must be a relative path within the current directory"
   - 测试 stdin 管道 → 成功，内容正确
   - 测试 `docs +update --doc TOKEN --mode overwrite --markdown -` → 成功修复
4. 修复：新脚本 `fix_feishu_docs.py` 用 `subprocess.Popen` + `stdin=PIPE` 直传内容；863篇走 `--mode overwrite`；39篇失败的走 `+create`；断点续传 `fix_progress.json`
5. **补充问题：文档所有者不是荣总**——`lark-cli config show` 显示 profile 是 `cli_a9528e80dc385bcf`（赵以纶），不是荣总的 `cli_a95d0d5f0e781bc9`。863篇全部以错误身份创建

## 第2层·原因

### 语义直觉替代了参数验证
- `--markdown` 看起来像"指定 markdown 文件"，实际是"传入 markdown 内容"——想当然直接用，没看 `--help`
- 命中「自然语言的模糊性」：关键词相同，语义不同

### 无声失败
- 863篇文档**创建全部成功**（返回码正常），但**内容全错**。状态码成功 ≠ 内容正确
- 批量前没有任何一条样本被人工核对——首件检验缺失

### 确定性约束持续被遗忘
- MEMORY.md 里白纸黑字写着"飞书文档所有者必须是荣总"，执行时仍用了错误 profile
- 与「流程执行力」同源：规则存在 ≠ 规则被执行

## 第3层·底层模型

> **语义直觉 ≠ 实际行为。** 参数的名称与文档是一手来源，直觉是二手来源。凡涉及 CLI 参数语义，必须看 `--help` 而不是猜。

> **无声失败比报错更危险。** 报错会中断，无声失败会静默地把垃圾铺满 863 篇。凡批量操作，必须设计"内容级校验"而非"状态级校验"。

> **「1-1-N」原则：** 1条 help 确认参数语义 + 1条数据验证内容正确 + 再放行 N 条批量。

## 第4层·能力

1. **CLI 参数前置阅读**：已知参数名不等于知道语义，`--help` 是 30 秒成本对 43 分钟返工
2. **首件检验**：批量写入的第 1 条必须验证**输出内容**（不是状态码）
3. **凭据/身份前置检查**：飞书操作前必须 `config show` 确认 profile

## 第5层·基本功

**对"看起来熟悉"的东西警惕性最低：**
- `--markdown` 是常见参数名，熟悉感压过了验证需求
- 863 篇的规模反而制造了"跑通就行"的心理——规模越大越要小样验证，实际做成了反过来
- **对格式/参数/身份这三类"确定性约束"，任何熟悉感都不构成免检理由**

## 下次要坚持的

1. **「1-1-N」原则**：批量操作先 1 条 help 确认 + 1 条数据验证内容 + 再放行 N 条
2. **飞书操作前必须 `config show` 确认 profile 是荣总的 app**（`cli_a95d0d5f0e781bc9`）
3. **lark-cli `--markdown` 三种用法**：① `--markdown "内容"` 直接传 ② `--markdown @./file.md` 相对路径文件 ③ `--markdown -` 从 stdin 读（最可靠，用 `subprocess.Popen` 管道）
4. **完成判据用源/目标量化对齐**（覆盖率 + 类型分布），不用接口返回码
